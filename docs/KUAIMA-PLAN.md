# 快马（Kuaima）协议方案

> 定位：以 naive、Trojan、天马为蓝本设计的新协议，不是天马的 TCP 延续，也不是 naive 的克隆。
>
> 约束：只有自签证书，没有 CA，没有域名；目标网络对 UDP 做 QoS、对 TCP 按流/端口限速，并重点打击 REALITY 类协议。

---

## 1. 目标与非目标

### 目标

1. 在只有自签证书的前提下，做到主动、被动探测都拿不到有效指纹；
2. 用 TCP 承载，绕开主要针对 UDP 的 QoS；
3. 一台服务器、一个进程、一个端口段，承载 100~500 Mbps，而不是靠堆 8~10 个入口；
4. 多节点集群，连接池并发，流量分摊到多个限速桶；
5. 继承天马的治理：目的地策略、连接/认证限流、按用户配额、内存水位；
6. 长连接优先，减少握手暴露。

### 非目标

- 不做 UDP 转发；
- 不做带宽聚合（总带宽仍受线路和运营商限制）；
- 不伪装成真实网站，不借别人的 SNI/证书，不走 REALITY 路线；
- 不自定义加密算法、不自定义多路复用、不自定义 ALPN；
- 不追求“像浏览器”，因为 obfs 门之后网络上看不到 TLS。

---

## 2. 蓝本分工

| 蓝本 | 取什么 | 不取什么 |
|---|---|---|
| naive | H2 CONNECT、多路复用、填充思路 | Chromium 网络栈、必须真站点 |
| Trojan | 单密码、极简认证、失败不回显 | 静态 SHA224、一连接一目标、smux |
| 天马 | obfs 门、exporter 绑定、治理、长连接优先 | QUIC、UDP、用户态拥塞控制 |

快马自己新增：

- 端口段部署；
- 客户端连接池与流调度；
- 每连接限速与降级迁移；
- 同协议多入口回退（只在 TCP 内切换，不引入 UDP）。

---

## 3. 总体架构

```
客户端
├── 入口池（多 IP / 多端口段）
│   ├── 入口 A：2~4 条长连接
│   ├── 入口 B：2~4 条长连接
│   └── 入口 C：...
├── 流调度器（按余量分摊）
└── 治理客户端（限速、健康上报）

        │ TCP
        ▼

服务端（一台机器一个进程）
├── 端口段监听（如 20000-20010）
├── obfs 门（错误 key 静默丢弃）
├── TLS 1.3（自签 + pin）
├── H2 服务
│   └── CONNECT host:port
└── 治理（policy / guard / quota / memory）
```

## 4. 线协议

### 4.1 分层

```
TCP
└── obfs 门
    └── TLS 1.3（自签，ALPN h2）
        └── H2
            ├── CONNECT host:port   → 代理流
            └── 其他                 → 404 或断开
```

### 4.2 obfs 门与密码轮换

**主密钥**

```
master = 用户在面板里设置的混淆密码
```

**时间窗口**

```
epoch = unix 秒 / obfs_rotation_seconds
（rotation 为 0 时固定 epoch = 0）
```

**每个分块的密钥**

```
key = BLAKE2b-256(master || "kuaima-obfs-rotate" || epoch)
```

**流分块格式**

TCP 是字节流，按块处理：

```
epoch(4) | salt(8) | len(2) | ciphertext
```

- `salt` 每块随机；
- `len` 最大 16 KiB；
- `ciphertext = plaintext XOR keystream`；
- `keystream` 用 `BLAKE2b-256(key || salt || counter)` 按 32 字节展开；
- 每块开销 14 字节，16 KiB 块可忽略。

**接收规则**

- `epoch` 在 `当前 ± tolerance` 内才接受；
- 窗口外、解密失败、长度异常：静默丢弃；
- 不回 RST、不回错误页、不做任何提示。

**轮换的意义与边界**

- 主密钥不变，泄露仍然全盘皆输；
- 轮换只限制“单个窗口密钥”的寿命；
- 长连接可以跨窗口继续，因为每块自带 epoch，不需要重连；
- 服务端和客户端必须使用相同的 `obfs_rotation_seconds` 和 `obfs_tolerance_seconds`。

**面板与订阅**

- 入站保存 `obfs_password`、`obfs_rotation_seconds`、`obfs_tolerance_seconds`；
- 订阅必须透传后两个字段，否则客户端解不开；
- 集群所有节点使用同一套参数。

### 4.3 TLS

- TLS 1.3；
- 自签证书，集群共用一张；
- 客户端 pin SPKI SHA-256；
- ALPN 只有 `h2`；
- SNI 不承载身份，可填固定占位名。

### 4.4 H2 与 CONNECT

请求：

```
:method: CONNECT
:authority: example.com:443
proxy-authorization: Kuaima <name>:<hex(token)>
```

- `token = TLS.ExportKeyingMaterial("kuaima", password, 32)`；
- 服务端校验通过回 `200`，之后双向 DATA；
- 失败回 `404` 或直接断流，不暴露代理语义；
- 每条流一个目标，天然多路复用。

### 4.5 为什么不用自定义帧

TLS 在 obfs 门里面，网络上看不到；再自定义帧只会增加实现风险，不会增加隐蔽性。H2 是成熟标准，直接用。

## 5. 认证

- 用户模型：`name + password`（Trojan 风格，不引入 UUID）；
- token 绑定当前 TLS 连接，不能重放；
- 认证在 CONNECT 头里完成，服务端无状态；
- 认证失败不区分“用户不存在”和“密码错误”；
- 同一连接可缓存认证结果，后续 CONNECT 可省略 token（可选优化）。

---

## 6. 连接与集群

### 6.1 端口段

- 服务端配置：`port_range: "20000-20010"`；
- 进程内为段内每个端口起监听；
- 面板只建一个 inbound；
- 防火墙只需放行整个段；
- 客户端从段内随机选端口建连接。

### 6.2 连接池

- 每个入口维持 1~4 条长连接；
- 需要更高吞吐时，在同一入口不同端口再开；
- 连接按五元组分散，对应不同限速桶；
- 连接数按“总需求 ÷ 单流实测值”自适应，默认上限 8。

### 6.3 长连接保持

- H2 PING：20 秒；
- TCP keepalive：idle 30s、interval 10s、count 3；
- 服务端空闲超时：300 秒；
- 建好的连接不主动断，避免反复握手。

### 6.4 流调度

每条连接记录：

- 实测吞吐；
- RTT；
- 丢包；
- 在途流数。

新流分配给“预计余量最大”的连接；某条吞吐低于基线 60% 持续 5 秒，标记降级，停止加流。

### 6.5 故障与重连

- 连接被 RST：新流切到健康连接；
- 重连指数退避 1~30 秒；
- 重连优先换端口，其次换入口；
- TLS session resumption 降低握手成本；
- 已建立流无法迁移，由应用重试。

### 6.6 集群

```
节点 A：进程 + 端口段
节点 B：进程 + 端口段
节点 C：进程 + 端口段
```

- 所有节点共享证书和用户表；
- 认证无状态；
- 客户端入口池按健康度和延迟选择；
- 配额默认每节点独立，二期可接 Redis 做跨节点聚合。

## 7. 抗 QoS

### 7.1 原则

总吞吐 = min(线路总带宽, Σ 每条流的可用额度)。

- 按流/端口限速：多开连接可叠加；
- 按 IP/用户总量限速：多开无效，只能换线路。

### 7.2 机制

1. **多连接**：同节点多端口、多节点，形成多个五元组；
2. **每连接限速**：客户端令牌桶，控制在实测稳定值的 80%~90%；
3. **pacing**：Linux 下设置 `SO_MAX_PACING_RATE`，避免突发；
4. **服务端 BBR**：内核拥塞控制，不用固定速率硬顶；
5. **降级迁移**：某条流被压，停止加流，新流换端口/入口；
6. **错峰建连**：不要同一秒连多个端口，避免扫描特征。

### 7.3 边界

- 运营商按 IP 总量限速时，快马无法突破；
- 流量分析仍可按时间、包长关联多条连接；
- 连接数不是越多越好，超过阈值行为异常。

---

## 8. 抗封锁

| 封锁 | 对策 |
|---|---|
| 封 IP | 多入口池、快速切换 |
| 封端口 | 端口段轮换，每条新连接换端口 |
| 协议识别 | obfs 门，错误 key 静默 |
| 主动探测 | 不回应未认证流量，不暴露 TLS |
| 长时间大流量 | 每流限速、多流分摊、错峰 |
| 整条 TCP 入口被封 | 换入口/换端口段，不切 UDP |

### 回退策略（只走 TCP）

- 客户端只配置快马入口，不配置 UDP/天马回退；
- 入口 A 连续失败 → 切入口 B/C；
- 同一入口内优先换端口段；
- 重连仍失败则失败关闭，等用户换入口或换订阅；
- 不自动切换协议，避免在 UDP 上额外暴露一个面。

为什么不做 UDP 回退：

- 多一套协议就多一套指纹和一套被封的入口；
- 回退时机的判断本身会暴露“主协议失败”这一事实；
- 一旦 UDP 被重点打击，回退等于主动把流量送到枪口；
- 宁可失败关闭、让用户换入口，也不自动切到另一条传输。

## 9. 治理

直接复用天马模块：

| 模块 | 行为 |
|---|---|
| policy | 默认拒绝私网、回环、链路本地；按需放行 |
| guard | 每 IP 连接数、认证失败封禁、每连接流数 |
| quota | 按用户流量配额与速率，端口段内共享 |
| memory | 进程级内存水位 |

与天马的区别：

- 没有 UDP 会话限制；
- 没有 obfs 轮换的额外配额；
- 配额按用户聚合，不按端口重复；
- 端口段内所有监听共享同一份治理状态。

## 10. 部署形态

### 服务端

```json
{
  "listen": "0.0.0.0",
  "port_range": "20000-20010",
  "certificate_path": "/etc/kuaima/cert.pem",
  "key_path": "/etc/kuaima/key.pem",
  "obfs_password": "master-secret",
  "obfs_rotation_seconds": 3600,
  "obfs_tolerance_seconds": 3600,
  "users": [{ "name": "alice", "password": "..." }],
  "policy": { "allow_private": false, "allow_loopback": false },
  "guard": { "max_connections_per_ip": 64 },
  "quota": { "bytes_per_period": 0, "max_rate_bps": 0 },
  "max_memory_mb": 512
}
```

- 一个进程；
- 一个端口段；
- 一张自签证书；
- 一份用户表；
- 一份治理配置。

### 面板

- 新增 `type: "kuaima"`；
- 入站字段：端口段、用户、证书、policy/guard/quota；
- 订阅只输出一条记录，带端口段；
- 不再为每个端口建 inbound。

### 客户端

- 入口列表：`host + port_range + pin + obfs_password + rotation + tolerance`；
- 连接池：每入口 1~4 条；
- 流调度与限速；
- 只配置快马入口，不与其他传输混用回退。

## 11. 目录结构（建议）

```
kuaima/
├── internal/
│   ├── obfs/          # 复用/改造 tianma obfs，改为流式
│   ├── wire/          # TCP 监听、TLS、H2
│   ├── proto/         # CONNECT 头、认证 token
│   ├── client/        # 入口池、连接池、调度器
│   ├── server/        # 端口段监听、H2 服务、CONNECT 处理
│   └── governance/    # 包装 tianma policy/guard/quota
├── boxapi/            # 给 sing-box 的门面
└── cmd/kuaima/        # CLI
```

复用方式：以 Go module 依赖 `tianma`，不复制代码；obfs 需要从“数据包”改为“流”，单独实现。

## 12. 分阶段实施

### P0：单节点最小闭环

- 一个端口；
- obfs + TLS + H2 + CONNECT；
- 单密码 + exporter token；
- 单条连接跑通 TCP 代理；
- 测单流吞吐。

### P1：端口段与多连接

- 端口段监听；
- 客户端连接池；
- 流调度；
- 每连接限速；
- 治理接入；
- 测聚合吞吐（目标：100 Mbps 用 ≤8 条连接）。

### P2：集群与回退

- 多入口池；
- 健康检查与故障切换（同协议多入口）；
- 面板 `kuaima` 类型；
- Windows / Android 客户端接入。

### P3：调优

- pacing 参数；
- 降级检测阈值；
- 填充与节奏扰动；
- 500 Mbps 场景 CPU 调优；
- 跨节点配额（可选 Redis）。

## 13. 验收指标

| 指标 | 目标 |
|---|---|
| 单流吞吐 | 达到线路的 50% 以上，或不低于同线路 TCP 直连的 80% |
| 聚合吞吐 | 100 Mbps 用 ≤8 条连接 |
| 建连时间 | 单连接 < 1 秒（局域网/同城） |
| 故障切换 | 新流 < 1 秒切到健康连接 |
| 长连接存活 | 空闲 10 分钟不断 |
| CPU | 500 Mbps 下单核占用可接受，必要时多连接分摊 |
| 治理 | 端口段内配额聚合正确 |

## 14. 风险与未决

1. **TCP RST 注入**：长连接可能被重置，需要多连接和快速切换；
2. **按 IP 总量 QoS**：协议无法突破，只能换线路；
3. **obfs 后是随机 TCP**：可能被“未知协议”规则拦截；
4. **端口段扫描特征**：同一 IP 多端口活动可能被关联；
5. **Go H2 性能**：500 Mbps 需要评估拷贝和 TLS 开销；
6. **客户端复杂度**：连接池、调度、回退都在客户端，sing-box 现有 outbound 模型不一定够，需要自定义适配；
7. **跨节点配额**：默认每节点独立，聚合需要额外组件；
8. **自签 pin 更新**：换证书要同步客户端配置。

## 15. 与三个蓝本的最终对照

| 能力 | naive | Trojan | 天马 | 快马 |
|---|---|---|---|---|
| 传输 | H2/TLS | TLS 裸流 | QUIC | TCP + obfs + TLS + H2 |
| 多路复用 | H2 | 无/smux | QUIC 流 | H2 |
| 认证 | Basic | 静态 SHA224 | exporter | 单密码 + exporter |
| 伪装 | 真站点 | 回落站点 | obfs 门 | obfs 门 |
| 证书 | 必须 CA | 可自签 | 自签 | 自签 |
| 集群 | 无 | 无 | 手动多节点 | 连接池 + 入口池 |
| 抗 QoS | 无 | 无 | 无 | 多流 + 限速 + 迁移 |
| 端口段 | 无 | 无 | 无 | 有 |
| 治理 | 无 | 无 | 有 | 继承 |

---

## 16. 一句话

快马是“**用 obfs 门解决自签下的探测问题，用 H2 多路复用解决连接模型，用端口段和连接池解决部署成本与吞吐，用天马治理解决边界**”的 TCP 协议；它不试图超过线路，只试图把线路真正用起来。
